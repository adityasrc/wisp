## Wisp: Building Reference

### Core purpose

Wisp is a **privacy/anonymity-oriented chat application** built primarily as a **learning and muscle-memory project**.

The real goal is not to build a massive messaging product. The goal is to repeatedly practice:

**Next.js/React + TypeScript → Node/Express → HTTP → WebSockets → PostgreSQL → pnpm monorepo**

Implementation is done **without AI assistance**. AI/external help is allowed for concepts, theory, and clarification. The project should naturally become complete through the implementation practice.

---

# 1. Identity & Account

Wisp is **username-first**, not phone-number based.

### Signup

Minimal onboarding:

* Username
* Password

No mandatory phone number or email.

The idea is that Wisp does **not try to prove that someone is a real-world person**. The platform only needs to know that an account controls its credentials.

### Username

* Must be unique.
* Certain usernames are permanently reserved.
* User can change username.
* Previous username remains reserved for **14 days**, giving the old owner a chance to reclaim it.
* Username-change frequency/policy can be refined later.

### Hidden permanent identity

Every user has a permanent internal identity that:

* never changes
* is not exposed to normal users
* is available to the platform/admin for abuse tracking

This allows a user to change usernames without losing platform-level accountability.

---

# 2. Discovery & Connection

Users discover each other through **username search**.

### Chat request

Unknown users cannot immediately start a conversation.

Flow:

```text
Search @username
      ↓
Send chat request
      ↓
Optional first message
      ↓
Recipient accepts / rejects / ignores
      ↓
If accepted → normal DM conversation
```

### One-message rule

Before the request is accepted:

> **Only one message can be sent with the request.**

No repeated messaging or spam before permission is granted.

This is one of Wisp's core product principles:

**permission before conversation.**

---

# 3. Conversations

The base conversation model is unified.

One `Conversation` concept can represent:

* **DM**
* **Group**
* **Channel**

The exact distinction comes from the conversation type/behavior rather than creating completely separate systems.

### V1 practical rollout

Initial focus:

**DM first**

Groups and channels can be introduced once the core system is stable.

### Groups

Later:

* Add existing connections
* Invite through shareable links
* Membership/roles

### Channels

Later:

* Broadcast-oriented conversation
* Different posting permissions

---

# 4. Messaging Philosophy

Wisp intentionally has stricter message rules than typical chat apps.

### Edit

A sent message can be edited for **15 minutes**.

After that:

> **Message becomes immutable.**

### Delete

No final deletion policy yet.

Current position:

> **Do not implement deletion until the policy is explicitly decided.**

The product philosophy is leaning toward preserving message history rather than allowing unrestricted deletion.

### Read receipts

**No read receipts.**

There is no "Seen" pressure.

We may track delivery internally, but users do not get the usual seen/read indicator.

Core idea:

> Until the recipient responds, the sender does not get a "seen" signal.

---

# 5. Product Differentiation

Wisp is **not trying to win by having more features than WhatsApp/Telegram**.

Its identity is:

### Privacy + identity control + low-pressure communication

Important existing differentiators:

* username-first identity
* no phone-number-based discovery
* chat requests
* one-message-before-acceptance rule
* recyclable usernames with a 14-day reclaim window
* hidden permanent platform identity
* no read receipts
* controlled editing
* stricter message-history philosophy

---

# 6. Additional Differentiators for V1

Two ideas were selected because they add interesting behavior without blowing up the scope.

## A. Dormant Connections

A connection can become **dormant** after a prolonged period of inactivity.

The exact inactivity period/policy is to be decided later.

Purpose:

* avoid permanently accumulating dead conversations/connections
* make the connection model more intentional

This should remain relatively lightweight.

## B. Message Lifespan

Messages can eventually have an optional lifespan/purpose.

Potential idea:

```text
Normal      → regular message
Sensitive   → expires after selected period
Important   → permanent
```

The exact UX/rules are still open.

This is a **later V1 feature**, not something to overdesign immediately.

---

# 7. Deferred V2 Idea

## Context-scoped identity / Multi-persona

A user could maintain multiple public personas/usernames while retaining one hidden permanent identity underneath.

Example:

```text
Permanent identity
        │
   ┌────┴────┐
   ↓         ↓
Work persona  Casual persona
```

This is intentionally **V2**.

Reason:

It is highly interesting and potentially one of Wisp's strongest differentiators, but it affects the fundamental data model:

* messages
* requests
* memberships
* conversation identity
* permissions

So adding it now risks turning the learning project into a huge architecture exercise.

**Keep the idea parked, not discarded.**

# 9. HTTP vs WebSocket responsibility

Important architecture rule:

### HTTP

Use for things like:

* signup
* login
* username search
* chat requests
* conversation history
* profile/settings
* other CRUD operations

### WebSocket

Use for realtime events:

* incoming messages
* message delivery
* connection status
* realtime conversation events

So:

```text
HTTP  → "Give me the messages."
WS    → "A new message just arrived."
```

The WebSocket backend still uses an underlying HTTP server because the WebSocket connection starts through an HTTP Upgrade/handshake.

For the current separate WS backend, a simple:

```ts
new WebSocketServer({ port })
```

is fine initially.

# 11. Development Philosophy

This is extremely important.

The project should **not become another huge side project**.

Every feature should answer:

> **Does building this help me practice the stack?**

If yes, build it.

If it only makes the product look fancy, defer it.

### Current priority

```text
Muscle memory
    ↓
Concept reinforcement
    ↓
Project progress
    ↓
Product differentiation
```

Not the other way around.

---

# 12. AI Rule

For implementation:

**No AI-generated code.**

You write the code yourself.

AI/external resources are allowed for:

* theory
* concepts
* architecture discussion
* documentation clarification
* understanding errors
* explaining something you genuinely don't understand

But not:

> "Write this feature for me."

The objective is that after building Wisp, you can look back at Verdict, Flowboard and Snip and recognize the patterns because **you implemented them yourself**.

---

# 13. Current build strategy

Do **not** build the app in isolated phases like:

> React for a week → Node for a week → WebSockets later.

Instead, use an **interleaved daily practice loop**:

```text
TypeScript / JS
      ↓
React / Next
      ↓
HTTP / Express
      ↓
WebSocket
      ↓
PostgreSQL
```

Each day touches a little of each.

That way the goal is not just project progress. It continuously reinforces the entire stack.

## Wisp's current product philosophy

> **A low-pressure, privacy-oriented communication app where people are identified by usernames rather than phone numbers, conversations require permission, identity can change publicly without losing platform accountability, and messaging isn't built around read-pressure or unrestricted history manipulation.**

And the project's bigger purpose remains:

> **Build it yourself, understand what you're building, and use it to make yourself less dependent on AI-generated code.**

This is the reference plan. Anything we add later should be judged against this scope first.
