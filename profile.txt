Haan, C + B genuinely combine ho sakta hai, aur actually yeh combination **dono ke individual weaknesses ko cancel kar deta hai** — chalo dekhte hain kaise.

## C + B ka logic

- **Default:** Discord-style generated avatar (koi upload nahi kiya to bhi identity-less, colorful avatar dikhta hai)
- **Optional:** User chahe to real photo upload kar sakta hai (full choice, koi forced restriction nahi)
- **Twist (B se):** Jab username change ho, agar photo **upload ki hui thi**, to wapas default generated avatar pe reset ho jaaye — user ko phir se manually decide karna padega ki naye username ke saath bhi wahi photo rakhni hai ya nahi

## Yeh kyun sahi combination hai

1. **User freedom intact hai** — koi bhi force nahi ho raha "sirf avatar hi rakho," jo tumhara point tha (agar koi khud ko dikhana chahta hai to dikha sake)
2. **Privacy philosophy bhi intact hai** — kyunki username change = automatic photo reset ka mतlab hai ki agar koi **genuinely fresh start** chahta hai, system usse protect karta hai (accidentally purani photo naye identity ke saath leak nahi hoti)
3. User ke paas **active choice** rehta hai — agar wo jaan-boojh kar same photo dubara upload kare naye username ke saath, wo uska decision hai, system use force nahi kar raha na rok raha hai

Yeh actually **better** hai pure Option B se, kyunki B mein "sabko force avatar-reset" tha, yahan sirf **default behavior safe hai, override user ke control mein hai.**

## Endpoints (updated)

```
GET    /api/users/me/avatar              # returns current avatar (generated or uploaded)
POST   /api/users/me/avatar              # upload custom photo (replaces generated one)
DELETE /api/users/me/avatar              # remove uploaded photo, revert to generated avatar
GET    /api/users/:username/avatar       # public fetch (works whether generated or custom)
```

**Internal logic (no separate endpoint, side-effect on username change):**
```
PATCH /api/users/me/username
  → on success:
      if avatar_type == "uploaded":
          avatar_type = "generated"
          avatar_url = null
          regenerate default avatar (based on new username/UUID hash)
```

## Schema implication (chhota sa)

`users` table mein do fields chahiye honge:
```
avatar_type   ENUM('generated', 'uploaded')
avatar_url    TEXT NULL   -- null if generated, else uploaded image URL
```

Generated avatar ke liye tumhe koi external image store karne ki zaroorat nahi — bas seed value (UUID ya username hash) client-side pe pass kar do, aur ek library (jaise DiceBear API/self-hosted) se render kar lo on the fly. Yeh storage bhi bachata hai.

Yeh design final lag raha hai? Agar haan, to ab hum poora **Postgres schema** (users, requests, conversations, messages, username_history) ek saath consolidate kar sakte hain — sab decisions ab tak ke incorporate karke.
